# Avanti — личный кабинет (вёрстка на Vue 3)

Вёрстка личного кабинета Avanti по макету Figma. Первый этап — только вёрстка,
без интеграции с API: все данные приходят из моков и заменяются реальными
ответами бэкенда на втором этапе.

## Что сделано

Свёрстаны 19 экранов, все подключены к роутеру. Роутинг — хеш-режим
(`createWebHashHistory`), поэтому адрес выглядит как `#/documents`: сборка
открывается с любого статического хостинга и из локального файла без
настройки сервера.

Порядок в таблице повторяет порядок маршрутов в `src/router/index.ts` —
это шаги оформления кредита, а за ними разделы кабинета и профиля.

изолированно; в самом кабинете они открываются кнопками.

Все экраны свёрстаны в двух ширинах макета — 1440px и 390px. Исключения,
где мобильного кадра в Figma нет и раскладка собрана по логике соседних
экранов: «Проверка банков-партнёров», «Договор» и «Подпись договора»
(см. раздел «Расхождения в макете»).

## Стек

- **Vue 3.5** — только сокращённый Composition API (`<script setup lang="ts">`)
- **TypeScript** в строгом режиме
- **Vite 6** — сборка и dev-сервер
- **SCSS** — модульные стили, BEM, дизайн-токены на CSS-переменных
- **Vue Router 4** — хеш-роутинг
- **ESLint + Stylelint + Prettier** — автоматическая проверка правил проекта

В рантайме проект зависит ровно от двух пакетов — `vue` и `vue-router`
(секция `dependencies` в `package.json`). Всё остальное — инструменты сборки
и проверок в `devDependencies`. Внешних UI-китов нет: все компоненты, включая
иконки, написаны с нуля.

## Запуск

```bash
npm install
npm run dev
```

Дальше открыть <http://localhost:5173>.

| Команда | Что делает |
| --- | --- |
| `npm run dev` | dev-сервер с HMR |
| `npm run build` | типизация + продакшн-сборка в `dist/` |
| `npm run preview` | локальный просмотр продакшн-сборки |
| `npm run lint` | все проверки разом (см. ниже) |
| `npm run format` | Prettier |

`npm run lint` последовательно выполняет:

| Шаг | Что проверяет |
| --- | --- |
| `lint:limits` | ни один файл не длиннее 300 строк |
| `lint:inline` | в шаблонах нет inline-стилей |
| `lint:js` | ESLint: правила Vue/TypeScript и правила проекта |
| `lint:css` | Stylelint: BEM-именование, порядок свойств, запрет hex вне токенов |
| `lint:format` | Prettier: единое форматирование |

## Соблюдение правил проекта

| Правило | Как выполнено |
| --- | --- |
| 1. Всё разносим по компонентам | Кнопка, бейдж, чекбокс, слайдер, аватар, каждая иконка — отдельные компоненты |
| 2. Один компонент = один файл | Один `.vue` — один компонент, без вложенных определений |
| 3–4. Доменное имя + назначение | Все файлы: `avanti_<домен>_<назначение>.vue` |
| 5. Не более 300 строк на файл | Проверяется скриптом `scripts/check_file_limits.mjs` в `npm run lint` |
| 6. Переиспользуемость | Данные и варианты — через `props`/`slots`, никаких зашитых строк внутри общих блоков |
| 7. Сокращённый Composition API | ESLint-правило `vue/component-api-style: ['script-setup']` |
| 8. Без inline JS и inline CSS | Отдельная проверка `scripts/check_inline_styles.mjs` в `npm run lint` — она падает на любом `style="..."` и `:style` вне единственного согласованного исключения. Штатное правило ESLint `vue/no-static-inline-styles` оставлено как дополнительная сетка, но оно ловит только литералы и привязку к переменной пропускает, поэтому основная проверка — скрипт. Вся логика — в `<script setup>`, всё оформление — в `<style lang="scss" scoped>` |

Дополнительно: Stylelint запрещает hex-цвета вне файла токенов (`color-no-hex`)
и проверяет BEM-именование классов.

### Единственное исключение по `:style`

В `avanti_range_slider.vue` через `:style` передаётся одно CSS-кастом-свойство
`--avanti-slider-progress` — доля заполнения слайдера. Это не оформление,
а передача динамического значения в CSS: все стили слайдера остаются в SCSS.
Без этого позицию ползунка невозможно связать с состоянием компонента.

## Дизайн-токены

Все цвета, тени, радиусы, семейства и насыщенности шрифтов вынесены
в `src/assets/styles/tokens.scss` как CSS-переменные с префиксом `--avanti-`.
В компонентах «сырые» значения не используются — при смене брендинга правится
один файл.

## Адаптив

Два опорных состояния из макета: 1440px и 390px.

- Где отличается только оформление — SCSS-миксины `mobile` / `desktop-up`
  (порог 768px).
- Где отличается сама структура разметки (шапка, нижняя навигация) —
  композабл `useIsMobile()`, чтобы не держать в DOM скрытые дубли.

Между 768px и 1024px раскладка тянется резиново; отдельного планшетного
макета в Figma нет — см. вопросы ниже.

### Экраны шире макета

По согласованию с заказчиком контент на широких экранах **не растягивается**:
его ширина остаётся макетной, а увеличиваются только боковые отступы.

| Раскладка | Ширина контента | Отступы на 1440px | Отступы на 1920px |
| --- | --- | --- | --- |
| Экраны мастера (симуляция, банки, одобрение) | 1240px | по 100px | по 340px |
| Экраны кабинета (главная, договор, IBAN, профиль) | 1296px | по 72px | по 312px |
| Карточка анкеты «Dati personali» | 1117px | по 161px | по 401px |

Ширины лежат в `_variables.scss`. Экраны мастера используют миксин
`content-container()` из `_mixins.scss`, экраны кабинета — ту же сетку через
`max-width` контейнера с боковыми отступами. Шапки считают ширину по той же
переменной, поэтому логотип и меню всегда стоят на одной вертикали
с содержимым страницы.

## Пиксельная точность

Вёрстка сверялась с макетом двумя способами: замером габаритов элементов
в браузере против размеров кадров Figma и попиксельным сравнением
скриншотов с эталонными выгрузками.

Габариты на 1440px совпадают с Figma:

| Элемент | Figma | Вёрстка |
| --- | --- | --- |
| Шапка личного кабинета | 1440×171 | 1440×171 |
| Карточка шагов | 792×130 | 792×130 |
| Баннер «завершите шаги» | 792×124 | 792×124 |
| Карточка «Dati personali» | 464×131 | 464×131 |
| Чеклист верификации | 464×483 @ y=163 | 464×483 @ y=163 |
| Контент симуляции | 1240×506 @ 100;161 | 1240×506 @ 100;161 |
| Кнопки навигации | 294×60 @ y=790 | 294×60 @ y=790 |
| Мобильная главная | 390×1139 | 390×1139 |

Отдельно учтено, что в Figma обводка кадра рисуется внутрь и не влияет
на его размер, а в браузере `border` прибавляется к габаритам. Поэтому
рамки карточек заданы миксином `inner-border()` — `inset`-тенью, которая
рисует ту же линию, не меняя размеров.

## Иконки

Иконки взяты из макета (векторные данные экспортированы из Figma) и оформлены
как компоненты: обводка — `currentColor`, размер задаёт контейнер, толщина
линии настраивается пропом `strokeWidth`. Благодаря этому одна иконка работает
во всех цветовых контекстах макета без дублирования файлов.

## Расхождения в макете (нужен ответ заказчика)

Ниже — все места, где макет противоречит сам себе, где кадра нет вовсе или
где решение принято за дизайнера. Каждый пункт продублирован комментарием
в коде: искать по словам `РАСХОЖДЕНИЕ МАКЕТА` и `НЕТ В МАКЕТЕ`.

Общее правило, которым мы руководствовались: если кадр есть — верстаем ровно
как в кадре, даже когда это выглядит ошибкой, и выносим значение в константы,
чтобы правка была в одну строку. Если кадра нет — собираем из уже
согласованных токенов и помечаем как несогласованное.

### Симуляция кредита

1. **Максимальная сумма кредита.** Десктоп показывает `33.000 €`,
   мобильная — `53.000 €`. Свёрстано как в макете, оба значения вынесены
   в `src/constants/avanti_simulation_config.ts` — нужно единое значение.
2. **Подпись минимального срока.** Десктоп: `1 mesi`, мобильная: `1 mese`.
   Грамматически верно `1 mese`. Свёрстано как в макете.
3. **Подпись строки платежа.** Десктоп подписывает её `Data di restituzione`
   («дата возврата»), хотя значение — сумма платежа в `€/mese`. Мобильная
   называет ту же строку корректно: `Rata di restituzione`. Обе подписи
   воспроизведены как в макете.
4. **Сумма в карточке итогов.** В поле ввода `12.000 €`, в карточке итогов
   `10 000 €` — в макете это разные значения. В вёрстке карточка считает
   платёж от введённой суммы; нужно подтвердить формулу расчёта платежа
   (сейчас аннуитет по ставке TAN 3,8%).

### Анкета «Dati personali»

5. **Поле «NUMERO DEL DOCUMENTO».** В макете собрано из компонента
   выпадающего списка и тащит за собой шеврон, хотя внутри — пример формата
   номера. Свёрстано обычным текстовым полем, шеврон убран.
6. **Блок «Acconsento al trattamento…» нарисован без чекбокса.** Если это
   юридическое согласие, обычно нужна явная отметка. Нужно подтверждение.

### Проверка банков-партнёров

7. **Мобильного кадра нет.** Раскладка на 390px собрана по логике соседних
   экранов мастера: боковые отступы 20px, те же размеры шрифтов, сетка
   банков в две колонки. Требуется подтверждение.

### Одобрение кредита

8. **Выделение срока.** Десктоп разбивает срок на два выделенных фрагмента
   («62» и «mesi»), мобильная выделяет их одним куском («62 mesi»).
   Реализован мобильный вариант — визуально они неразличимы.

### Личный кабинет и карточка «Dati personali»

9. **Содержимое карточки.** В поле `Cognome` (фамилия) в макете стоит
   название банка `Intesa Sanpaolo S.p.A.`, а в `Nome` (имя) — имя и фамилия
   целиком. Значения оставлены как в макете; на этапе интеграции сюда придут
   данные пользователя из API.
10. **Две строки с одинаковой подписью.** В расширенной карточке подпись
    `Tipo di documento` повторяется дважды, хотя по имени слоя вторая
    строка — номер документа. Текст оставлен как в макете.

### Запрошенные документы

11. **Зоны перетаскивания файла (drag & drop) в макете нет ни в одном кадре.**
    Загрузка в Figma идёт кнопкой «Carica il documento». Зона свёрстана,
    но её тексты придуманы, поэтому по умолчанию она скрыта и включается
    пропом `showDropzone`. Нужно решить: рабочий drag & drop или UI-заглушка,
    и оставлять ли блок вообще.
12. **Строка загруженного файла.** В макете обе подписи одинаковые
    («Foto del documento»), размер файла не показан. По заданию строка
    выводит имя, размер и статус — размер добавлен в моковые данные.
13. **Фон плашки ошибки.** В макете `#fff6f6`, розового тона в палитре
    токенов нет вообще. Использована белая поверхность из палитры — нужен
    либо новый токен, либо подтверждение текущего варианта.

### Договор

14. **Мобильного кадра нет.** На 390px две колонки выстраиваются в один
    поток, а таблица амортизации прокручивается вбок. Нужно подтвердить:
    горизонтальный скролл таблицы или перестроение в карточки.
15. **Имя заявителя не сходится.** В шапке договора — `ERDF RFDC`,
    в карточке личных данных — `Marco Rossi`. Значения оставлены как
    в Figma; на интеграции сюда придут данные API.
16. **Источник текста договора.** Статичный текст или приходит из API,
    и нужен ли экспорт в PDF — не определено.

### Подпись договора

17. **Мобильного кадра нет.** Раскладка на 390px собрана по логике
    соседних модальных окон.
18. **Способ подписи.** Макет показывает статичную область подписи,
    реализован рабочий canvas. Нужно подтвердить, требуется ли он уже
    на этапе вёрстки или достаточно статичной модалки.

### IBAN и вывод средств

19. **Ползунок суммы.** Нарисовано только крайнее правое положение
    («8.300 € / 8.300 €», 100% доступного). Минимум и шаг подобраны так,
    чтобы верхняя граница всегда была достижима; нужны значения заказчика.
20. **Способ «Carta».** Раскрыт только способ «IBAN», поля перевода на
    карту в макете не нарисованы — набор собран по смыслу и требует
    подтверждения.

### Оплата комиссии

21. **Первый шаг мастера не спроектирован.** Полоса показывает три шага
    «1. IBAN / 2. COMMISSIONE / 3. COORDINATE», но во всех двадцати окнах
    комиссии активным нарисован только шаг 2 или 3. Кадра с активным шагом 1
    нет. Сейчас шаг 1 собран из тех же блоков, что и шаг 2 — придумывать ему
    собственный текст нельзя. Варианты: (а) прислать кадр; (б) поставить
    первым шагом уже свёрстанный ввод IBAN из потока документов;
    (в) начинать полосу со второго шага. **Нужен ответ до сдачи.**
22. **Порядок блоков расходится по ширинам.** На десктопе поясняющая
    плашка стоит над карточкой суммы, на мобильной — под ней. Порядок
    переставляется свойством `order`, разметка одна.
23. **Знак «?» у способа оплаты на шаге 3.** Поясняет SEPA Instant, но кадра
    с таким окном в Figma нет, поэтому обработчик намеренно не подключён.
